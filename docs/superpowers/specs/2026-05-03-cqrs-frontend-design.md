# CQRS Frontend Design

## Summary

Build a small Vue 3 + Vite frontend in a new `vue/` app to visualize and exercise the planned CQRS write/read API. The UI is intentionally simple: multiple tabs, each with create and get flows, basic tables for response data, and a shared request log showing recent endpoint calls and responses.

The backend API is not fully implemented yet, so the frontend should be structured around real HTTP calls and easy endpoint reconfiguration, but it must not depend on mock data. The goal is to make the frontend immediately usable once endpoints land, while remaining easy to adapt if path or payload details change.

## Goals

- Create a standalone frontend app under `vue/` using `pnpm`, Vue 3, Vite, and Vue Router.
- Expose separate tabs for the main CQRS entities and interactions.
- Support at least create and get operations on each relevant tab.
- Show raw response data in simple tables or detail blocks.
- Keep the design intentionally minimal and readable.
- Centralize API access through `VITE_API_BASE_URL`.
- Make endpoint definitions easy to update as the backend stabilizes.

## Non-Goals

- No mock server or fake data fallback.
- No advanced state library.
- No complex data grid, filtering system, or design system.
- No optimistic updates or reactive CQRS polling layer.
- No full CRUD parity beyond the requested create/get baseline.

## User Experience

The frontend is a developer-facing console rather than a polished product UI. It should feel like a clean internal tool for manually exercising the write side and observing returned read-side data.

### Navigation

Top-level navigation uses tabs routed with Vue Router:

- `Users`
- `Messages`
- `Emails`
- `Requests`

Each tab is its own route so links are stable and the code stays separated by feature.

### Layout

Each entity tab uses the same simple structure:

1. Page header with short explanation.
2. Create form.
3. Get form.
4. Result section rendered as either:
   - simple key/value detail rows for single objects, or
   - simple HTML tables for arrays.
5. Inline error box if the last request failed.

The `Requests` tab shows a chronological log of recent HTTP requests made from the UI, including method, URL, status, duration, and response body preview. This acts as the lightweight CQRS process visualization the user asked for: endpoint calls are explicit and inspectable without building diagrams.

## Functional Design

## Users Tab

### Create

Provide a form for creating a user. Initial assumed fields:

- `email`

The form must not ask for `id`. User identifiers are assumed to be generated by the backend database as an autoincrement primary key and returned in the response.

Submit as `POST` to the configured users endpoint.

### Get

Provide a form for fetching a user by identifier. Initial assumed inputs:

- `id`

Fetch from the configured user read endpoint and render a single-record detail view. If the backend later exposes list endpoints, the page structure can accommodate them without redesign.

## Messages Tab

### Create

Provide a form for creating a message. Initial assumed fields:

- `user_id`
- `subject`
- `content`
- `date_sent`

Submit as `POST` to the configured messages endpoint.

### Get

Provide a form for fetching messages. Since `docs/PLAN.md` may still evolve, this flow should be implemented through a configurable endpoint helper that can support either:

- get by message id, or
- get by user id / owner id

The initial UI should expose the minimal field set needed for the first implemented read endpoint. The code should keep this logic isolated in the API layer so adapting it does not require a component rewrite.

Results render in a simple table.

## Emails Tab

### Create

Provide a form for attaching an email to a user. Initial assumed fields:

- `user_id`
- `address`
- `category`
- `importance`

Submit as `POST` to the configured email endpoint.

### Get

Provide a form for fetching user email associations. Initial assumed input:

- `user_id`

Results render in a simple table.

## Requests Tab

The requests tab displays recent request history collected by a shared in-memory store:

- timestamp
- method
- full URL
- request body preview
- status or network error
- response body preview
- elapsed time in milliseconds

This is not a persistent audit log. It exists only in the current browser session.

## Architecture

## App Structure

Create a separate Vite app in `vue/` with a conventional structure:

- `src/main.ts`
- `src/App.vue`
- `src/router/`
- `src/views/`
- `src/components/`
- `src/api/`
- `src/stores/` or a lightweight composable-based state folder
- `src/types/`
- `src/assets/`

## API Layer

The API layer is the most important stability boundary because backend endpoints are not finalized.

It should provide:

- one shared HTTP helper around `fetch`
- typed request helpers per resource
- centralized endpoint path builders
- uniform error normalization
- request logging hooks

This keeps endpoint churn localized to `src/api/`.

## State Management

Use only Vue Composition API primitives. A full state library is unnecessary.

Shared state should be limited to:

- request log entries
- maybe small shared helpers for loading/error state patterns

Each tab owns its own form state and latest result state.

## Visual Design

The visual direction stays intentionally plain:

- light theme
- neutral colors
- boxed sections
- standard inputs and buttons
- compact but readable spacing

Avoid decorative CQRS diagrams. The process is visualized by:

- separated resource tabs
- explicit create/get forms
- visible request history
- raw structured responses

## Error Handling

The frontend must distinguish:

- backend non-2xx responses
- network failures
- invalid JSON responses

For each failed request:

- show a visible error block in the current tab
- record the failure in the request log
- keep the last successful result unless replaced intentionally

## Testing

Given the scope, keep testing focused:

- unit tests for API helper behavior if test tooling is already straightforward in the Vite setup
- otherwise at minimum ensure the project builds cleanly

Verification for implementation should include:

- dependency install with `pnpm`
- production build
- basic lint/typecheck if added

## Open Assumptions Made Explicit

Because the backend is not ready, this design assumes:

- separate endpoints will exist for users, messages, and emails
- each resource will support at least one create and one get flow
- `VITE_API_BASE_URL` is the correct integration boundary
- exact path and payload shapes may still change

To avoid ambiguity, the frontend should encode endpoint definitions in a single configuration file or module so those changes are local edits rather than cross-app refactors.

## Recommended Implementation Order

1. Scaffold `vue/` with Vite, Vue, TypeScript, Router, and `pnpm`.
2. Add global app shell and tab navigation.
3. Implement shared API client and request log store.
4. Implement `Users` tab.
5. Implement `Messages` tab.
6. Implement `Emails` tab.
7. Implement `Requests` tab.
8. Add styling and verification.

## Scope Check

This scope is appropriate for a single implementation pass. It is intentionally narrow: one small frontend app, four routes, real HTTP integration, and no advanced client architecture.
